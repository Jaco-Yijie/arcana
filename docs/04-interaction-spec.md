# Arcana — Tarot Table 交互方案（Agent 4 / Interaction 输出）

> 上游事实来源：`docs/00-brief.md`（§8 随机机制、§9 各阶段交互、§15–20）、`docs/01-product-spec.md`（AC-01~AC-07、G-01~G-10、G-21、G-22）。

## 0. 全局基线（六节共用，先读这一节）

### 0.1 引擎边界

交互层**不做任何随机决策**。所有牌序变化只能通过 `@/features/table/engine` 的三个入口发生：

```ts
applyShuffleGesture(deck, entropy, gesture, seed) // 洗牌，需要一次真实手势
applyCut(deck, ratio, entropy)                    // 切牌，ratio 必填、无默认值
cardAt(deck, index)                               // 选牌，纯查表、零随机
```

`computeFanLayout` / `hitTestFan` 只算坐标，不碰牌。
**UI 里出现 `Math.random()` 决定任何与牌有关的东西 = G-01，直接打回。**

### 0.2 Pointer Events（指针事件）基线

统一用 Pointer Events，不写 `touchstart` / `mousedown` 双份逻辑，也不依赖 `hover`（G-20）。

```ts
el.addEventListener('pointerdown', onDown)   // 立刻 el.setPointerCapture(e.pointerId)
el.addEventListener('pointermove', onMove)   // 手指移出元素也不会丢事件
el.addEventListener('pointerup', onUp)
el.addEventListener('pointercancel', onCancel) // 来电/系统手势打断，必须复位状态
```

三条硬规则：

1. `pointerdown` 里**立刻** `setPointerCapture(e.pointerId)`，`pointerup` / `pointercancel` 里 `releasePointerCapture`。移动端手指在快速划动中很容易滑出元素边界，不捕获就会丢 `pointerup`，牌会卡在拖拽态。
2. 只处理 `e.isPrimary === true` 的指针。多指同时按不做多点手势（本产品不需要），第二根手指直接忽略。
3. 每个手势状态机必须有 `pointercancel` 分支，且分支行为 = 完全回滚到手势开始前（**不产生任何 entropy、不改牌序**）。

### 0.3 `touch-action` 分配表

`touch-action` 是移动端手势冲突的第一道也是最有效的一道防线。全表如下，Frontend 直接照抄：

| 区域 | `touch-action` | 理由 |
|---|---|---|
| 洗牌牌堆 `.shuffle-pile` | `none` | 洗牌要吃掉所有方向的拖动，不能让页面跟着滚 |
| 切牌牌堆 `.cut-pile` | `none` | 同上，切牌线要跟手 |
| 摊牌滚动容器 `.fan-scroller` | `pan-x` | 只把**横向**滚动交给浏览器原生（惯性顺滑），纵向手势留给「上滑抽牌」 |
| 摊牌里的单张牌 `.fan-card` | 继承（不设） | 由父容器统一管，卡牌自己不劫持 |
| 摆牌区被拖动的牌 `.dragging-card` | `none` | 拖拽期间禁止页面滚动 |
| 牌位 Drop Zone | `none` | 避免释放瞬间触发滚动 |
| 已翻开的牌 | `auto` | 它已经锁定，恢复正常页面行为 |
| 整个 `/table/*` 页面根节点 | `pan-y` + `overscroll-behavior: contain` | 允许纵向滚页面，但禁止 iOS 下拉刷新/回弹穿透 |

另外全局加：`.table-root { -webkit-user-select: none; user-select: none; -webkit-touch-callout: none; }` —— 否则长按牌堆会弹出系统「拷贝/查询」菜单，仪式感当场破功。

### 0.4 轴锁定（Axis Lock）—— 拖拽与横滑冲突的统一解法

摊牌区同时存在三种手势：**横滑浏览**、**上滑抽牌**、**点选**。解法是一个共用的判定器，不要每个组件各写一套：

```
pointerdown              → 记录 (x0, y0, t0)，状态 = 'undecided'
pointermove 累计位移 < 10px  → 状态仍 'undecided'，什么都不做
pointermove 首次跨过 10px    → 锁定主轴，此后不再改判：
      |dx| >= |dy|  → 'scroll'（横滑浏览，交还给原生滚动）
      |dx| <  |dy|  → 'lift'  （上滑抽牌，preventDefault）
pointerup 且始终 'undecided' 且 (now - t0) < 500ms → 'tap'（选牌）
```

- **10px** 是判定阈值：低于它一律当作静止。低了会把手抖判成滑动，高了会让 tap 感觉迟钝。
- **一旦锁定不再改判**。中途改判是移动端最常见的"手感很奇怪"来源。
- `'scroll'` 分支必须**不** `preventDefault`，让 `overflow-x: auto` 的原生惯性接管；`'lift'` 分支必须 `preventDefault`（配合 `touch-action: pan-x` 才有效）。

### 0.5 动画规格（framer-motion 12）

| 用途 | duration | ease / spring |
|---|---|---|
| 牌堆错位（洗牌反馈） | 260ms | `[0.22, 1, 0.36, 1]` |
| 牌堆重组咬合 | 340ms | `[0.22, 1, 0.36, 1]`，stagger 8ms |
| 切牌分离 | 420ms | `[0.16, 1, 0.3, 1]` |
| 切牌落叠 | 380ms | `[0.34, 1.2, 0.64, 1]`（末端一点点回弹 = 重量） |
| 扇形展开 | 620ms | stagger 6ms，`[0.16, 1, 0.3, 1]` |
| 牌被拿起 | 180ms | `spring { stiffness: 420, damping: 32 }` |
| 拖拽回弹 | — | `spring { stiffness: 300, damping: 28 }` |
| 落入牌位 | 220ms | `[0.2, 0.9, 0.3, 1]` |
| 翻牌 | 520ms | `[0.32, 0.72, 0, 1]` |

全站遵守 `prefers-reduced-motion`：命中时所有位移动画压到 120ms 线性，翻牌改为交叉淡入，**但手势本身一个都不能省**——减少动画不等于减少用户操作。

### 0.6 性能：不要真的渲染 78 个 DOM 节点做动画

洗牌 / 切牌阶段牌堆是**背面朝上的一叠**，用户看不出有几张。渲染 **14 个代理层**（proxy layer）即可，配 `will-change: transform`。摊牌阶段确实需要 78 个可点节点，但只有进入视口 ±2 屏的才挂 `motion.div`，其余渲染成静态 `div`（`transform` 由 `computeFanLayout` 一次算好，不参与动画）。

## 1. 洗牌 Shuffle（`/table/shuffle`）

> 红线：**G-03 洗牌不能是一个按钮**。AC-02 要求「没操作 → 牌序绝不变；操作过 → 牌序必须可验证地变」。

### 1.1 手势设计

页面中央一叠背面朝上的牌。用户可以在牌堆上做两类动作，**都是自由拖动，没有"正确姿势"**：

| 手势 | 判定 | 映射到的洗牌手法 |
|---|---|---|
| 纵向拖动 / 搓动 | `|dy| >= |dx| / 1.2` | **riffle 交切洗**：牌堆掰成两叠交错咬合 |
| 横向滑动 | `|dx| > |dy| * 1.2` | **strip 切叠洗 / overhand**：从一端抓下小叠反序叠回 |

阈值与分段规则：

- **有效位移阈值 24px**（`MIN_SHUFFLE_DISTANCE`）。低于它 = 误触，引擎直接返回 `applied: false`，牌序与 entropy 都不动。这是 AC-02 上半段的实现保证。
- **一次按住可以洗很多次**。用户真实的洗牌动作是"来回搓"，所以在一次 `pointerdown … pointerup` 期间做 **stroke 分段**：
  - 主轴方向发生**反转**（`dx` 或 `dy` 符号翻转且反向位移已超过 24px）→ 结算上一段，计一次洗牌；
  - 或单段累计位移达到 **140px** → 强制结算，计一次洗牌；
  - `pointerup` 时若尾段位移 ≥ 24px → 结算最后一段。
  - 每段结算调用一次 `applyShuffleGesture`，`shuffleCount` +1。
  - 结算之间加 **90ms 冷却**，防止高频 `pointermove` 把一次抖动切成十次洗牌。
- **entropy 采样**：`pointermove` 中每累计 ≥ 12px **或** 距上次采样 ≥ 60ms，调用一次 `recordDrag(entropy, { dx, dy, dt })`。不要每帧都采（`timings` 只留 32 个，采太密等于只留下最后半秒）。

**这里没有「洗好了」按钮以外的任何按钮**，尤其没有「帮我洗」「洗 3 次」「跳过」。

### 1.2 视觉反馈

跟手阶段（`pointermove`，尚未结算）：

- 14 个代理层按 `dy`（或 `dx`）做**递减位移**：第 i 层偏移 `offset_i = drag * (1 - i / 14) * 0.35`，形成"整叠被推歪"的错层。
- 每层 `rotate = drag_x * 0.008deg`，上限 ±3°。牌堆边缘出现极窄的高光线（1px，`opacity 0.25`），模拟纸牌侧面。
- 全程 60fps，只用 `transform`，不改 `top/left`。

结算瞬间（一次洗牌完成）：

- **riffle**：两叠向左右分开 42px（90ms）→ 交错咬合回中心（340ms，stagger 8ms，用引擎返回的 `packets` 决定每叠有几层参与），末端有 4px 的过冲回弹。
- **strip**：一叠从侧面被抽出 → 上移 28px → 压回顶部（380ms）。`rotatedPacket: true` 时这一叠在压回途中做一次 180° 的**侧向翻转**（`rotateZ 180deg`，不是 `rotateY`——不能露出牌面，G-05）。
- 音效：`shuffle.mp3` 一次纸牌摩擦声（≤ 200ms），Haptic `vibrate(8)`。设置里可关。
- 计数器从 `已洗 N 次` 变成 `已洗 N+1 次`，数字做一次 1.12 倍的 pop（120ms）。**只报数，不评价**——不能出现「洗得不错」「差不多了」这种引导用户何时停手的文案。

### 1.3 状态机

```
type ShuffleStage =
  | 'idle'        // 牌堆静置，等用户上手
  | 'dragging'    // 按住并移动中，牌堆跟手错位
  | 'settling'    // 一段 stroke 结算中，播放重组动画（90ms 冷却期）
  | 'ready'       // shuffleCount >= 1，"去切牌"可用；仍可继续洗
```

| 迁移 | 条件 |
|---|---|
| `idle → dragging` | `pointerdown` 落在牌堆内 |
| `dragging → dragging` | `pointermove`，累计位移 < 24px（不结算，只跟手） |
| `dragging → settling` | 方向反转 / 单段 ≥140px / `pointerup` 且尾段 ≥24px |
| `settling → dragging` | 冷却 90ms 结束且指针仍按住 |
| `settling → ready` | 冷却结束且指针已抬起，`shuffleCount ≥ 1` |
| `dragging → idle` | `pointerup` 且尾段 < 24px（误触，什么都不发生） |
| `* → idle` | `pointercancel`（回滚，不产生 entropy） |
| `ready → cut 阶段` | **用户点「去切牌」**，无自动迁移 |

### 1.4 用户如何知道该他动手 / 已完成 / 如何进下一步

- **该他动手**：进入页面 600ms 后，牌堆做一次极轻的呼吸位移（±6px，1.6s 循环），配文案「滑动牌堆进行洗牌。」（简报 §19 原文）。首次进入时文案常驻；第二次起 3s 后淡出到 `opacity 0.35`（AC-13）。
- **这一步已完成**：`shuffleCount ≥ 1` 后，底部「去切牌」从 `opacity 0.3 / pointer-events: none` 变为可用，同时计数器常显。**注意：这只是"可以走了"，不是"该走了"**——不弹提示、不高亮、不倒计时。洗多少次是用户的事。
- **进下一步**：只有一条路——用户主动点「去切牌」。没有"洗满 3 次自动进入"，没有停手 5 秒自动进入。

### 1.5 实现要点

1. `applyShuffleGesture` 的第四个参数是 `session.shuffleSeed`，**必须传**。这是 `systemRandom + userInteractionEntropy` 里的 systemRandom 那一半。
2. `gesture.startRatio` / `endRatio` 是**手势起止点落在牌堆上的纵向位置比例**（牌堆顶端 = 0）：`(e.clientY - pileRect.top) / pileRect.height`，`clamp(0, 1)`。它主导 riffle 的切割点——用户从牌堆上方推还是下方推，掰开的位置就不一样，这个因果关系用户能感知到。
3. `durationMs` 用 `performance.now()` 差值，不要用 `Date.now()`。
4. 每次结算后同步整个 session 到 localStorage（简报 §15）。entropy 已做 32 条 `timings` 上限，写入体积约 220 bytes，可以每次都写。
5. 引擎是纯函数、返回新对象，直接 `setState({ deck, entropy })` 即可，不要就地修改。

### 1.6 反模式（这一步最容易做错成什么样）

| ❌ 错误做法 | 为什么错 |
|---|---|
| 一个「洗牌」按钮 + 一段 3 秒动画 | G-03，核心价值当场归零 |
| 拖动只播放预设动画，牌序其实是拖完之后统一 `shuffle()` | 手势成了动画触发器，等价于按钮 |
| 手势幅度不影响结果（拖 10px 和拖 300px 一样） | G-21，entropy 沦为装饰 |
| 「已洗 3 次，建议进入下一步」 | 系统在替用户决定何时洗够 |
| 洗牌时露出任何一张牌的正面 | G-05 / AC-07 |
| 牌堆用 78 个 DOM 节点做 spring 动画 | 移动端直接掉到 20fps，"重量感"变成"卡" |
| 用 `touchmove` + `preventDefault` 但没设 `touch-action: none` | iOS Safari 上首帧仍会滚动，手感发飘 |

## 2. 切牌 Cut（`/table/cut`）

> 红线：**G-04 系统不得自动切牌，不得提供随机切点或默认切点**。AC-03：不同切点必须产生不同牌序。

### 2.1 手势设计

牌堆改为**侧视图**（edge view）：一叠横躺的牌，能看见 78 道细密的牌缘线。这是切牌唯一说得通的视角——用户要选的是"从第几张切开"，不是"点哪张牌"。

- **按下即定位**：`pointerdown` 落在牌堆上，立刻在触点高度出现一条**切牌线**（1px 冷金色，两端各有一个小三角把手）。`ratio = (e.clientY - pileRect.top) / pileRect.height`。
- **按住可微调**：`pointermove` 实时更新 `ratio`，切牌线跟手，上下两叠的厚度实时变化，旁边显示 `上 32 / 下 46`（张数）。这个数字是让用户知道"我切在哪"，不是让他去凑整。
- **抬手即切**：`pointerup` → 调用 `applyCut(deck, ratio, entropy)` → 播放分离与重组动画。**不弹确认框**。
- **可以再切**：动画结束后有一个「再切一次」的弱化入口。切几次是用户的事，每次都记入 `entropy.cutPositions`。
- 切牌线**在 `pointerdown` 之前完全不存在**。不预设在中点，不预设在任何位置——预设就是默认切点，就是 G-04。
- 引擎把 `ratio` 夹在 `[0.05, 0.95]`，保证"切了一定看得出变化"，避免用户切在最边缘却发现什么都没发生。

### 2.2 视觉反馈

1. **跟手**：切牌线随指移动，线两侧的牌缘做 2px 的分离预览（上叠整体上移 1px，下叠下移 1px），暗示"就要从这里断开"。
2. **分离**（420ms）：上叠向右上方移出 64px 并轻微抬起（`scale 1.02`，投影加深），下叠留在原位。中间露出一道空隙。
3. **重组**（380ms）：**下叠先向上平移到顶部**，上叠再压到它下面——这是实体切牌的物理顺序（下半叠放到上面），也正是引擎 `[...lower, ...upper]` 做的事。末端 `[0.34, 1.2, 0.64, 1]` 的一点点过冲 = 落叠的重量。
4. 音效：`place.mp3` 一次闷响；Haptic `vibrate(12)`（比洗牌重一点，因为这是一个"决定"）。
5. 重组完成后，牌堆恢复正视图，出现「摊开牌」按钮。

### 2.3 状态机

```
type CutStage =
  | 'idle'      // 牌堆侧视，无切牌线
  | 'aiming'    // 按住中，切牌线跟手
  | 'splitting' // 分离动画
  | 'merging'   // 重组动画
  | 'done'      // 已切过至少一次，"摊开牌"可用；仍可"再切一次"
```

| 迁移 | 条件 |
|---|---|
| `idle → aiming` | `pointerdown` 落在牌堆内 |
| `aiming → aiming` | `pointermove` 更新 `ratio` |
| `aiming → splitting` | `pointerup`（**唯一触发切牌的事件**） |
| `aiming → idle` | `pointercancel` 或指针移出牌堆上下边界 24px 以上后抬起（视为放弃） |
| `splitting → merging` | 分离动画结束 |
| `merging → done` | 重组动画结束 |
| `done → aiming` | 用户点「再切一次」后再次 `pointerdown` |
| `done → 摊牌阶段` | **用户点「摊开牌」**，无自动迁移 |

### 2.4 用户如何知道该他动手 / 已完成 / 如何进下一步

- **该他动手**：侧视牌堆本身就是"这里可以切"的暗示。配文案「选择一个你想切开的位置。」（简报 §19 原文）。首次进入时，牌堆侧面有一道极缓慢上下游走的微光（3s 循环，`opacity 0.12`），扫过整个可切范围，告诉用户"整条边都能切"。第二次起不播。
- **这一步已完成**：重组动画的落叠是明确的完成信号，加上 `上 32 / 下 46` 变成 `已切于第 32 张`。
- **进下一步**：用户点「摊开牌」。没有"切完自动摊开"。

### 2.5 实现要点

1. `applyCut` 的 `ratio` 参数**没有默认值**，函数签名强制调用方提供。这是把 G-04 写进类型系统。
2. 侧视图的 78 道牌缘线用一个 `repeating-linear-gradient` 画，不要用 78 个 div。切牌线位置用 `top: ${ratio * 100}%`。
3. 牌堆高度不要太小——建议 **≥ 220px**。太矮的话 78 张牌挤在一起，`ratio` 的一个像素等于 0.35 张牌，用户会觉得"我根本切不准"。220px 高度下 1 张牌 ≈ 2.8px，配合实时张数显示，足够精确。
4. 顶部/底部各留 **12px 的死区**不响应 `pointerdown`，避免用户想滚页面时误切。
5. `applyCut` 返回的 `cutIndex` / `upperCount` / `lowerCount` 直接喂给动画，不要自己再算一遍——自己算会和引擎的 `drift` 偏移对不上，动画和结果就会不一致。

### 2.6 反模式

| ❌ 错误做法 | 为什么错 |
|---|---|
| 切牌线默认停在中点 | 默认切点 = G-04，且诱导所有人都切在一半 |
| 提供「随机切」「帮我切」 | G-04 明文禁止 |
| 点击即切（无按住微调） | 移动端手指粗，点哪算哪的体验是"我没得选" |
| 切完弹「确定要这样切吗？」 | G-10 精神，用状态表达而不是弹窗 |
| 动画只是把牌堆抖一下，没有真的分成两叠 | AC-03 要求"可见地重组" |
| 牌堆用正视图（一张牌背）做切牌 | 用户不知道自己在切什么，位置感为零 |
| 切完自动进入摊牌 | 剥夺了"我切完了，我准备好了"的确认权 |

## 3. 摊牌 Fan Spread（`/table/draw` 第一屏）

> 简报 §9：默认横向 / 扇形展开，**全部背面朝上**，可左右滑动浏览，用户可从任意位置选择。

### 3.1 手势设计

- **横向滑动浏览**：`overflow-x: auto` + `touch-action: pan-x` + `-webkit-overflow-scrolling: touch`。用原生滚动，不要自己实现惯性——自己写的惯性在 iOS 上永远比原生差一截。
- **不做吸附（snap）**：`scroll-snap-type` 会把浏览变成"翻页"，用户失去"我在整副牌上游走"的连续感。
- **展开动画**：进入页面时 78 张从牌堆位置扇形展开，stagger 6ms（总计约 620ms）。这段动画期间禁止选牌（`pointer-events: none`），避免"还没摊好我就点中了"。
- **初始滚动位置**：`scrollOffsetForIndex(input, 39)`，即整副牌的中段。不从最左边开始——从中间开始才有"一副牌摊在我面前"的感觉，也避免所有用户都从第 0 张开始选。
- 选牌手势见 §4，两者共用 §0.4 的轴锁定判定器。

### 3.2 布局规格（由 `computeFanLayout` 计算，UI 不要自己算）

375px 宽屏、卡牌 92×156 的实测值（自检脚本第 7 节已验证）：

| 指标 | 值 |
|---|---|
| 相邻牌间距 `step` | 28px |
| 每张牌露出宽度 `exposure` | 28px（= `MIN_EXPOSURE`，手指可点下限） |
| 扇形总宽 `contentWidth` | 2280px |
| 可滚动距离 `maxScrollOffset` | 1905px |
| 边缘牌倾角 | ±8°（视口边缘），上限 ±12° |
| 弧线深度 | 22px（中心高、两侧低） |
| 中心提示区 | 半径 110px 内，`scale` 最高 1.06，上浮最高 14px |

**弧线锚定在视口中心而不是扇形中心**：用户滚到哪里，弧顶就跟到哪里，屏幕正中的那几张永远是抬起来的。这保证"从任意位置选择"是真的——不会出现"只有扇形正中那几张看起来可选"。

### 3.3 视觉反馈

- 全部统一牌背（简报 §21）。**牌背图案必须有轻微的逐张差异**（`hue` 微偏 ±3、星点位置随 index 变化），否则 78 张完全一样的矩形看起来像一个条形码贴图，"一整副牌"的感觉出不来。差异必须**与牌面无关**（只跟 index 走），否则就是变相泄露（AC-07）。
- 滚动时中心区的牌持续上浮/落下，形成一条"呼吸的弧"。这个效果只靠 `computeFanLayout` 的 `focused` / `scale` / `y`，滚动事件里重算即可，不需要 IntersectionObserver。
- 已被拿走的牌位置留**空缺**（该 index 的牌不渲染，其余牌**不重排**）。空缺是重要信息：它告诉用户"我从这里拿的"。重排会让用户彻底失去位置记忆。

### 3.4 状态机

```
type FanStage =
  | 'dealing'   // 扇形展开动画中，不可交互
  | 'browsing'  // 可滚动浏览、可选牌
  | 'picking'   // 某张牌正被拿起（见 §4）
  | 'complete'  // 已拿满牌阵所需张数，扇形淡化到 opacity 0.45
```

| 迁移 | 条件 |
|---|---|
| `dealing → browsing` | 展开动画结束（约 620ms） |
| `browsing → picking` | 轴锁定判定为 `'tap'` 或 `'lift'` |
| `picking → browsing` | 该牌已进入手牌区 / 手势被取消 |
| `browsing → complete` | `drawn.length + placements.length === spread.cardCount` |
| `complete → browsing` | 用户把某张牌从牌位拖回（换牌，见 §5） |

### 3.5 实现要点

1. **两套命中判定，按渲染方案选**：
   - DOM 方案（推荐）：78 个绝对定位的 `div`，`zIndex` 直接用 `computeFanLayout` 给的值，浏览器的事件冒泡天然就会命中最上层——这时不需要 `hitTestFan`。
   - Canvas / 单一手势层方案：必须用 `hitTestFan(layouts, x, y)`，它返回 `zIndex` 最高的那张。**千万不要写成"遍历找到第一个包含该点的牌"**——那会命中被压在最下面、用户根本看不见的牌，是移动端选牌误触的头号来源。
2. 坐标转换：`x = e.clientX - scrollerRect.left`，`y = e.clientY - scrollerRect.top`。`computeFanLayout` 的 `scrollOffset` 传 `scroller.scrollLeft`，算出来的 `x` 就已经是相对可视区的，两边对得上。
3. 滚动时用 `requestAnimationFrame` 节流重算布局，不要在 `scroll` 回调里直接 `setState`（iOS 上 `scroll` 事件频率极高）。
4. 78 张全渲染没问题（都是简单 div），但**只给视口 ±2 屏内的挂 `motion.div`**，其余用静态 `div` + `transform`。
5. `containerHeight` 建议 ≥ 320px，否则弧线深度 22px + 上浮 14px 会让边缘牌被裁掉。

### 3.6 反模式

| ❌ 错误做法 | 为什么错 |
|---|---|
| 只摊开 10~20 张"代表" | 简报 §9 要求"感觉是完整一副牌" |
| 摊开时有任何一张正面朝上 | G-05 / AC-07 |
| 牌间距小于 28px | 手指点不中，AC-15 挂 |
| 加 `scroll-snap` | 浏览变翻页，失去连续游走感 |
| 拿走一张后其余牌重排补位 | 用户丢失位置记忆，"我从这里拿的"消失 |
| 自己实现横向惯性滚动 | 永远比原生差，且和轴锁定互相打架 |
| `hitTest` 返回第一个匹配而不是最上层 | 用户点 A 拿到 B，最恶劣的一类 bug |
| 给牌背加 hover 效果作为唯一提示 | G-20，移动端没有 hover |

## 4. 选牌 Select

> 简报 §9：用户必须从牌背中**主动选择**某一张。AC-01：点击后不得现场随机。

### 4.1 手势设计

两种都支持，用户用哪种都行：

| 手势 | 判定 | 语义 |
|---|---|---|
| **Tap** | 轴锁定判定为 `'tap'`（位移 < 10px 且 < 500ms） | 拿起这张牌 |
| **上滑抽出** | 轴锁定判定为 `'lift'`，且向上位移 ≥ 48px | 拿起这张牌（更有"抽"的实感） |

- 上滑过程中牌跟手上移，**未达 48px 就松手 → 回弹归位**（spring 300/28），不算选中。这个"差一点就抽出来了"的手感非常重要：它让"抽出来"变成一个需要用点力气的动作。
- 上滑到 48px 的瞬间给一次 `vibrate(8)` + 牌边缘微亮，告诉用户"到了，可以松手了"。
- 已经被拿走的位置不可再选（该 index 不渲染）。
- 拿满牌阵所需张数后，扇形整体淡化，继续 tap 无效（不弹提示，用状态表达）。

### 4.2 从"位置"到"牌"

```ts
// 唯一正确写法
const entry = cardAt(session.deck, deckIndex)   // 纯查表
```

**点击事件的整条调用链里不允许出现任何随机数生成**（AC-01）。自检脚本第 5 节做了两重验证：78 个 index × 100 次调用结果全部恒定，且等于由 seed + 操作序列独立重算出的值。

拿起后：`drawn.push({ deckIndex, pickedAt: Date.now() })`。**牌面依旧不解析、不渲染、不写进 DOM** —— `DeckEntry` 只在翻牌那一刻才拿去查牌义（AC-07）。

### 4.3 视觉反馈

- 拿起动画（180ms spring）：牌从扇形位置飞到屏幕下方的**手牌区**（hand area），途中 `scale` 1.0 → 1.08 → 1.0，`rotate` 归零。这段位移是有目的地的，不是随机飞散。
- 手牌区固定在底部，最多同时持有 1 张。**已经拿着一张牌时不能再拿第二张**——必须先把手上这张放进牌位。这避免了"拿了 5 张不知道哪张是哪张"的混乱，也让每一次选牌都对应一次明确的摆牌决定。
- 扇形上留下空缺（见 §3.3）。
- 音效：`pick.mp3` 轻微纸张滑动声。

### 4.4 状态机

```
type SelectStage =
  | 'idle'      // 没拿牌，可以选
  | 'lifting'   // 上滑跟手中，尚未达阈值
  | 'held'      // 手上有一张牌，等待摆放（此时不能再选）
```

| 迁移 | 条件 |
|---|---|
| `idle → lifting` | 轴锁定为 `'lift'` |
| `lifting → held` | 上滑位移 ≥ 48px 后 `pointerup` |
| `lifting → idle` | 位移不足就松手（回弹）/ `pointercancel` |
| `idle → held` | 轴锁定为 `'tap'` 且 `pointerup` |
| `held → idle` | 牌被摆入牌位（§5）或被放回扇形 |

### 4.5 实现要点

1. Tap 判定必须用**自己实现的轴锁定 + `pointerup`**，不要用 `onClick`。`onClick` 在滚动结束后有概率误触发（iOS 的 300ms 与滚动惯性叠加）。
2. 手牌区的牌用 `layoutId` 与扇形中的那张关联，framer-motion 的 `layout` 动画会自动生成从扇形到手牌区的位移路径，不需要手算坐标。
3. 上滑跟手时把该牌的 `zIndex` 临时提到最大，否则它会被右边的牌压住，看起来"抽不出来"。
4. `pickCard(deckIndex)` 必须幂等：已在 `drawn` 或 `placements` 里的 index 直接返回原状态（防连点）。

### 4.6 反模式

| ❌ 错误做法 | 为什么错 |
|---|---|
| 点击后才 `randomCard()` | G-01 / AC-01，最严重的红线 |
| 「随机帮我选 3 张」 | 剥夺选择权，等价于系统替用户抽牌 |
| 选中后立刻显示牌名 | AC-07，翻牌环节的意义直接归零 |
| 允许一次拿多张再统一摆 | 用户记不住哪张是哪张，摆牌变成瞎放 |
| 未翻开的牌把 `cardId` 写进 `data-*` 属性 | AC-07 明确要检查 DOM |
| 用 `onClick` 而不是 pointer 手势 | 滚动惯性误触发 |

## 5. 摆牌 Drag to Position

> 红线：**G-06 禁止自动飞入 / 点击即落位**。AC-04：只用点击（无 `pointermove`）必须永远无法把牌放进牌位。

### 5.1 手势设计

- 手上有牌时，牌阵的空牌位以虚线轮廓显示（`SpreadPosition.x/y` × 容器尺寸换算）。
- 用户按住手牌区的牌拖动。**必须发生 `pointermove` 位移 ≥ 10px 才进入拖拽态**——这条判定就是 AC-04 的实现：没有 move 就没有拖拽，没有拖拽就永远落不了位。
- **吸附半径 56px**（牌中心到牌位中心）。进入半径内：牌位高亮，**但牌不动**。牌永远严格跟着手指，一毫米都不能自己走。
- 释放时：在半径内 → 220ms 落位动画；不在 → 300/28 spring 回弹到手牌区。
- **换牌**（AC-06）：已摆放且 `revealed === false` 的牌可以直接拖离牌位，牌位恢复为空，该牌回到手牌区，可以重新摆或放回扇形换一张。**全程不弹 Confirm Dialog**（G-10）。
- `revealed === true` 的牌：`draggable = false`，`pointerdown` 直接忽略。不弹"已锁定"的警告，用视觉状态表达（见 5.3）。

### 5.2 吸附反馈的克制程度（简报 §9 原话："要克制"）

允许：牌位轮廓从虚线变实线、`scale` 1.0 → 1.04、边缘 `box-shadow` 出现 8px 的冷色微光（`opacity ≤ 0.4`）、一次 `vibrate(6)`。

禁止：牌位放大超过 1.06、脉冲呼吸动画、粒子、连线、"释放以放置！"的浮动文字、牌被磁力拉过去。

### 5.3 视觉状态表达（替代弹窗）

| 状态 | 视觉 |
|---|---|
| 空牌位 | 虚线轮廓 + 牌位名（如"过去"），`opacity 0.5` |
| 空牌位 + 手上有牌 | 虚线变亮，`opacity 0.9` |
| 吸附范围内 | 实线 + `scale 1.04` + 微光 |
| 已放置未翻开 | 牌背 + 牌位名移到下方；牌有极轻的可拖拽暗示（长按 400ms 后轻微抬起 2px） |
| 已翻开（锁定） | 牌位名变实心底色，卡牌投影收紧贴地，**去掉所有可拖拽暗示**——"这张已经定了"通过它不再"浮着"来表达 |

### 5.4 状态机

```
type PlaceStage =
  | 'idle'       // 手上有牌，未开始拖
  | 'dragging'   // 拖拽中
  | 'hovering'   // 拖拽中且落在某个 Drop Zone 吸附范围内
  | 'placed'     // 已落位（revealed = false，可拿回）
  | 'locked'     // 已翻开，不可再动
```

| 迁移 | 条件 |
|---|---|
| `idle → dragging` | `pointerdown` + `pointermove` 累计 ≥ 10px（**缺一不可**） |
| `dragging ↔ hovering` | 牌中心进入 / 离开某牌位 56px 半径 |
| `hovering → placed` | `pointerup` |
| `dragging → idle` | `pointerup` 在任何牌位半径外 → 回弹 |
| `* → idle` | `pointercancel` → 回弹 |
| `placed → dragging` | 用户重新按住并拖动（换牌） |
| `placed → locked` | 该牌被翻开（§6） |
| `locked → *` | **无出口**。已翻开不可替换（AC-06 / G-09） |

### 5.5 实现要点

1. 两种实现都可以，但**必须保证"没有 `pointermove` 就绝对不落位"**：
   - framer-motion：`<motion.div drag dragSnapToOrigin onDragEnd={...}>`，在 `onDragEnd` 里判断距离。注意 `dragMomentum={false}`，否则松手后牌会自己滑一段，看起来像"系统在帮我放"。
   - 手写 Pointer Events：`setPointerCapture` + `transform: translate3d(...)`，最可控。
2. Drop Zone 的坐标由 `SpreadPosition.x/y`（0–1 相对坐标）× 牌阵容器尺寸换算，容器用 `aspect-ratio` 固定比例，保证 375px 和 430px 屏上牌阵形状一致。
3. 拖拽期间给 `body` 加 `overflow: hidden`，防止 iOS 橡皮筋。
4. 5 张牌阵在 375px 宽屏上会比较挤：牌位卡牌缩到 64×108，牌位间距至少 12px，**Drop Zone 的判定半径不要因此缩小**——判定区可以比视觉区大，这是移动端的常规做法。
5. 摆放顺序完全自由。不要求"必须先摆第一个牌位"，不要在用户摆错顺序时提示。

### 5.6 反模式

| ❌ 错误做法 | 为什么错 |
|---|---|
| 点击牌位就把牌放过去 | G-06 / AC-04 |
| 靠近就自动吸过去（松手前牌已就位） | AC-04 明确禁止"释放前自行完成移动" |
| 牌位有"推荐放这里"的提示 | 系统替用户决定牌位归属 |
| 拿回牌时弹「确定要换掉吗？」 | G-10 |
| 已翻开的牌还能拖 | G-09 / AC-06 |
| 摆满后自动翻牌 | G-07 |
| 吸附时牌位放大 1.3 倍 + 脉冲光圈 | 简报 §9"要克制"，且滑向抽卡 UI |

## 6. 翻牌 Reveal（`/table/reveal`）

> 红线：**G-07 无"全部翻开"/自动翻开/倒计时；G-08 无爆炸粒子、大量闪光、SSR 抽卡表现、强烈震动**。AC-05：逐张由用户触发。

### 6.1 手势设计

| 手势 | 判定 | 说明 |
|---|---|---|
| **Tap** | 位移 < 10px 且 < 500ms | 翻开这一张 |
| **上滑** | 向上位移 ≥ 32px | 翻开这一张（简报 §9 的"轻微上滑"） |

- 上滑过程中牌跟手上移并轻微 `rotateX`（最多 8°），**未达 32px 松手 → 回落**。同样的"差一点"手感。
- **一次只翻一张**。翻牌动画进行中（520ms），其余牌的 `pointer-events` 关闭，防止连点连翻——连点翻开三张会让每一张的仪式感全部消失。
- 翻牌**顺序完全自由**，用户想先翻哪张就先翻哪张。不做"必须按牌位顺序翻"。
- 已翻开的牌再点 = 展开/收起牌义第一层，**不会翻回去**（结果不可逆）。

### 6.2 视觉反馈（重量感怎么做）

翻牌动画分三段，总计 520ms，`ease [0.32, 0.72, 0, 1]`：

| 时间 | 动作 |
|---|---|
| 0–120ms | 牌略微**抬起**：`y -10px`，`scale 1.03`，投影从 8px 扩散到 20px 并变淡 |
| 120–400ms | `rotateY 0° → 180°`，`perspective: 1200px`。**在 90° 前后 40ms 内换面**（`backface-visibility: hidden` + 两层结构），确保没有一帧能看到牌面的镜像 |
| 400–520ms | 落回：`y 0`，`scale 1.0`，投影收紧到 6px 并加深 |

**"重量感"来自那 10px 的抬起与落回**，不是来自光效。一张牌如果原地翻转、投影不变，看起来就是一张贴图在转，而不是一张纸被翻过来。

允许的光效（简报 §9"可有极轻微 Glow"）：翻转完成后一道 **240ms** 的柔光从牌面斜扫而过，`opacity 0 → 0.3 → 0`，宽度约卡牌宽度的 40%，无颜色偏移。**仅此一项。**

Haptic：翻转开始时 `vibrate(10)`。落回时不再震——两次震动会变成"游戏反馈"。

音效：`flip.mp3`，一次干脆的纸张翻面声，≤ 260ms。

翻开后立刻显示牌义第一层（简报 §11）：`The Hermit — 逆位｜内省 · 独处 · 寻找方向`。**不铺满屏幕**，只在卡牌下方一行。

### 6.3 状态机

```
type RevealStage =
  | 'idle'       // 该牌背面朝上，等待用户
  | 'lifting'    // 上滑跟手中，未达阈值
  | 'flipping'   // 翻转动画中（全局互斥）
  | 'revealed'   // 已翻开，锁定
```

页面级：

```
type RevealPhase =
  | 'pending'    // 还有牌没翻开
  | 'allRevealed'// 全部翻开，展示完整牌阵 + "开始完整解读"按钮
```

| 迁移 | 条件 |
|---|---|
| `idle → lifting` | 该牌上滑手势开始 |
| `lifting → flipping` | 上滑 ≥ 32px 后 `pointerup` |
| `lifting → idle` | 位移不足松手 / `pointercancel` |
| `idle → flipping` | Tap |
| `flipping → revealed` | 动画结束（520ms） |
| `revealed → *` | **无出口** |
| `pending → allRevealed` | 最后一张 `flipping → revealed` |
| `allRevealed → Reading` | **用户点「开始完整解读」**（AC-10 / G-11：不自动跳转、不自动弹出） |

### 6.4 用户如何知道该他动手 / 已完成 / 如何进下一步

- **该他动手**：未翻开的牌有极轻的浮动（`y ±3px`，2.4s 循环，各牌相位错开）。已翻开的牌完全静止。**"还在浮着 = 还没翻"** 是一个不需要文案的状态语言。首次进入配文案「准备好后，翻开它。」（简报 §19 原文）。
- **进度**：顶部 `1 / 3 已翻开`。纯计数，不催促。
- **这一步已完成**：全部翻开后，牌阵整体轻微上移 12px 并居中（280ms），底部出现「开始完整解读」。
- **进下一步**：只有用户点按钮。**AC-10 明确要求翻完最后一张不得自动跳转或弹出 Reading。**

### 6.5 实现要点

1. 牌面数据**在 `flipping` 状态开始的那一刻才 mount**。在 `idle` / `lifting` 阶段，DOM 里不能有 `cardId`、牌名、牌义的任何痕迹（AC-07 会检查 DOM）。
2. 3D 翻转结构：外层 `perspective: 1200px`，内层 `transform-style: preserve-3d` + `rotateY`，正反两面都设 `backface-visibility: hidden`，背面 `transform: rotateY(180deg)`。
3. iOS Safari 上 `preserve-3d` 与 `overflow: hidden` 的父级会打架 —— 翻牌容器的所有祖先都不要设 `overflow: hidden`。
4. 翻牌互斥用一个页面级 `flippingId: string | null`，不为 null 时其余牌 `pointer-events: none`。
5. `revealed` 的牌写回 session 时带 `revealedAt`，Session 恢复后必须保持已翻开状态（G-22，自检脚本第 8 节已验证牌序与朝向的恢复一致性）。
6. `prefers-reduced-motion` 时：翻转改为 260ms 的交叉淡入（背面淡出、正面淡入），**手势不变**。

### 6.6 反模式

| ❌ 错误做法 | 为什么错 |
|---|---|
| 「全部翻开」按钮 | G-07，明文禁止 |
| 摆满后自动逐张翻开 | G-07 |
| 翻牌爆金光 / 粒子 / 光柱 / 稀有度框 | G-08，直接滑向抽卡 UI |
| 强烈震动 / 多次震动 | G-08 |
| 翻完最后一张自动跳 Reading | G-11 / AC-10 |
| 翻牌可以翻回去 | 结果必须不可逆 |
| 90° 时能看到牌面镜像 | 穿帮，且轻微泄露（AC-07） |

## 8. 如果把所有 AI 解读功能全部删除，这个抽牌过程本身是否依然值得体验？

**结论：按本方案实现，是——但它的价值来源和很多人以为的不一样，而且有三个前提条件必须成立，缺一个就变成"否"。**

### 8.1 诚实的判断

先说清楚一个容易自欺的地方：抽牌过程**本身不提供信息**。删掉 AI 之后，用户拿到的只有三张牌名、正逆位和 15 个关键词。如果我们指望"用户看到 The Hermit 逆位就自己悟了"，那是把责任推给用户，属于自欺。

那它凭什么还值得体验？凭三件 AI 给不了的东西：

1. **一个可被自己认领的随机结果。** 用户拖了 7 次、切在第 32 张、选了第 41 个位置——他知道换一个动作结果就完全不同（自检脚本第 8 节验证过：切点差 0.01、最后一次手势差 1px，抽到的牌就全变）。这不是"系统给了我一张牌"，是"我这一次的手，落在了这里"。这个感受和解读文字无关，删掉 AI 它一分都不掉。

2. **一段有明确身体节奏的中断。** 搓牌、切开、浏览 78 张、抽出、放下、翻开——每一步都必须用手完成，都需要几秒钟，都不能跳过。它把"我在想一件事"这件事从脑内拖到了手上。这是所有正念类产品在做但大多做砸的事，塔罗的物理流程天然自带这个结构。

3. **一个非自己选择的切入角度。** 用户带着"我要不要换工作"进来，牌面给的关键词是"独处 · 寻找方向"。这个词不是他选的，也不是系统按他的问题挑的（G-12 禁止 AI 影响牌序）。**它的价值恰恰在于它没被优化过。** AI 解读只是把这个角度说得更顺，角度本身在翻开牌的那一刻就已经产生了。

### 8.2 三个前提条件（不成立就变成"否"）

**前提一：每一步的操作必须真的改变结果，而且用户要能感知到这种因果。**
如果洗牌手势只播动画、牌序其实是背后统一 `shuffle()` 的，那第 1 条价值直接归零，整个流程退化成"过场动画"。这就是为什么引擎里手势的距离/方向/时长/起止位置全部实质参与置换，为什么自检脚本要专门验"同方向仅距离不同 → 结果不同"。**这一条是整个产品的地基。**

**前提二：牌义第一层必须足够好，好到没有 AI 也能自己站住。**
这是当前方案的**真实短板**，也是我要在这里明确提出的问题：现在的第一层只有"牌名 + 正逆位 + 3–5 关键词"，删掉 AI 之后，这就是用户拿到的全部内容。三个孤立的词撑不住一次占卜的收尾。

> **改进建议（需 Lead 决策，属 Data / Content Agent 范围）**：牌义数据里为每个 `SpreadPosition` 增加一句 **"这张牌落在这个牌位上"的定位句**（模板化即可，不需要 AI）。例如「隐士 · 逆位 · 落在『阻碍』」→「你可能一直在等一个更清楚的方向，而这份等待本身正在拖住你。」这是静态数据，不是 AI，成本是 5 个牌阵 × 若干牌位 × 正逆位的文案量。有了它，删掉 AI 之后用户仍然能读到一段完整的东西。

**前提三：结尾必须给用户一个"自己说话"的位置。**
删掉 AI 之后，流程的终点是一片空白。所以**塔罗日记的"我的笔记"必须从可选变成翻牌后的自然下一步**——牌阵全部翻开后，除了「开始完整解读」，同一屏上应有一个同等分量的入口：「先写下你看到的」。

> **改进建议（需 Lead 决策，属 Journal / Frontend Agent 范围）**：`allRevealed` 状态下并列两个入口，且「先写下你看到的」在视觉上不弱于「开始完整解读」。这同时解决了另一个问题：**AI 先说话会污染用户自己的判断**。让用户先写，再看解读，塔罗"整理问题、提供观察角度"的定位（Product Spec §1.4）才真正落地。

### 8.3 一句话回答

**删掉 AI，这个过程依然值得体验——因为它的核心从来不是"牌告诉我什么"，而是"我亲手把一个不可预测的结果确定了下来，并且必须自己面对它"。**
AI 解读是这段体验的**放大器**，不是它的**发动机**。发动机是引擎里那套 `systemRandom + userInteractionEntropy`，和这份文档里六个不能跳过的手势。

反过来说也成立：**如果抽牌过程做砸了（洗牌是按钮、切牌自动、点击即落位、一键全翻），那再好的 AI 解读也救不回来**——那时用户拿到的只是一段包装成塔罗的随机文本生成器，而这正是产品简报第 0 条要防的东西。

# Arcana V2 — 接入 DeepSeek LLM 塔罗解读引擎 · Product Scope（Product Agent 输出）

> 上游事实来源：`docs/00-brief.md`、`docs/01-product-spec.md`（AC-01~15 / G-01~G-24）、`docs/06-qa-report.md`。
> 本文件只定义 V2 的**产品边界与验收**，不含实现方案与 Prompt 全文。与 V1 冲突处，本文件仅在明确写出「本轮修订」的条目上生效，其余一律以 V1 为准。

---

## 1. 本轮核心价值 Core Value

1. V1 的解读是**牌义字典的拼接**：每张牌各说各的，牌与牌之间没有关系，整篇没有叙事，也没有回到用户最初的问题。V2 要把它变成**一次真正的读牌**。
2. 「像读牌」的可操作定义只有三条：**牌与牌之间被联系起来**（组合、冲突、密度、顺序）、**整组牌被讲成一个连贯的故事**、**故事最后回到用户写下的那个问题**。三条缺一，本轮就没做成。
3. LLM 的职责边界在本轮**收得比 V1 更紧**：它只能对「已经完全确定的牌」做解释。抽牌、牌序、正逆位、牌阵、牌位全部在调用发生之前就已冻结，LLM 是**读者**，永远不是**发牌人**。
4. 接入真实 API 不能降低 V1 的可靠性下限：**没有 Key、断网、限流、模型抽风，产品都必须仍然能用**——Mock 解读是一直保留的兜底，不是过渡方案。
5. **否决规则（用于砍功能）**：任何功能，如果它 ① 让 LLM 以任何形式接触或影响「抽到哪张牌」，② 让用户在失败时丢掉已经抽出的牌，③ 把解读从「一次读牌」推向「一个聊天机器人」，一律否决——即使它更聪明、更好玩、更容易实现。

**冲突解决优先级**：核心产品价值 > 用户体验 > 技术便利 > 视觉效果。（延用 V1）

## 2. Scope 边界

### 2.1 In Scope 范围内

| # | 模块 | 内容 |
|---|---|---|
| S1 | Reading Provider 抽象 | `ReadingProvider` 接口 + `MockReadingProvider`（复用现有 `mockReading.ts`）+ `DeepSeekReadingProvider`，由 `READING_PROVIDER` 切换 |
| S2 | 服务端解读接口 | 新增最小后端，**唯一**一个解读端点；API Key 只存在于服务端环境变量 |
| S3 | 结构化解读输出 | 固定 JSON 契约（§4），服务端做 Schema 校验，前端**不解析 Markdown 长文** |
| S4 | Card Relationship 分析 | 大小阿卡纳密度 / 花色重复 / 元素重复与冲突 / 数字模式 / 正逆位比例 / 相邻牌 / 开始→中间→结尾 / 支持牌 / 冲突牌 / 转折点 / 主导主题 —— **有意义才出现** |
| S5 | 语言红线运行时校验 | 禁语与空洞表达在服务端校验；命中即重试一次，仍命中则降级 Mock |
| S6 | 错误与降级 | Key 缺失 / 401 / 403 / 429 / 5xx / 网络错误 / 超时 / 非法 JSON / 空 content / Schema 校验失败，共 10 类全覆盖 |
| S7 | Loading 分阶段 | 阶段性文案（描述**系统在做什么**），不伪装模型思维链 |
| S8 | Retry 重试 | 前端可重试，payload 与首次**逐字节相同**；牌不重抽 |
| S9 | V1 兼容层 | 新 Reading 结构与 V1 `Reading` 类型并存，历史日记 100% 可读、可展示、可分享 |
| S10 | 隐私告知 | 首次触发在线解读时一次性告知「你的问题与牌面会发送到第三方模型服务」，用户可拒绝并继续用 Mock |
| S11 | 配置与密钥卫生 | `.env.example`、`.gitignore`、无 `VITE_*` 前缀、无硬编码 |

### 2.2 Out of Scope 范围外（含预判的 Scope Creep）

**A. V1 已拒绝的一律继续拒绝**：简报 §26 全表 + Product Spec §2.2 全表。本轮不重开任何一条。

**B. 本轮新出现的蔓延项，逐条裁决**：

| 蔓延项 | 裁决 | 理由 |
|---|---|---|
| 流式输出（SSE / 逐字打印） | **收**（不做） | 结构化 JSON 与流式天然冲突——半个 JSON 无法校验、无法渲染，Schema 校验必须拿到完整响应。而且逐字打印会诱导用户把它当「模型在思考」，正撞 §7 的红线。等 UI 契约稳定后再评估 |
| 多轮对话式塔罗师 | **收**（不做） | 直接违反 G-13。追问一旦变成多轮上下文累积，Context 边界必然失守，产品会滑成 ChatGPT Clone（G-18） |
| 把追问（Follow-up）也接 LLM | **收**（本轮不做，进 Backlog V2.1） | 本轮痛点是「单次解读不像读牌」，不是「追问不够聪明」。追问是多轮入口，风险面比单次解读大一个量级。**重启条件**：单次解读的语言红线与 Schema 校验在真实流量下稳定两周以上，且追问被设计为「单轮、无累积、Context 仍受 AC-12 限制」 |
| 用户自定义 Prompt / 高级设置里填 System Prompt | **收**（不做） | 用户改 prompt = 绕过所有语言红线与「不参与抽牌」约束，等于把 G-12/G-14 的执行权交出去 |
| 解读质量评分 / 点赞点踩 / 反馈收集 | **收**（不做） | 需要后端存储与账号体系（G-17 未解除部分），且会把塔罗变成可打分的商品，与「不替你做决定」的定位冲突 |
| 多语言解读（英文/日文） | **收**（不做） | 简报 §26 明确不做多语言。且禁语表与语气校验是中文特化的，多语言会让红线校验直接失效 |
| 让 LLM 推荐牌阵 / 优化问题 | **收**（不做） | 牌阵推荐与问题优化保持 Mock。牌阵决定牌位结构，让 LLM 介入就是让它间接影响牌面结构（G-12） |
| 让 LLM 判定高风险话题（医疗/财务/法律） | **收**（不做） | 安全边界必须是**确定性**的。继续用本地 `safety.ts` 判定，判定结果作为约束**输入**给 LLM，不由 LLM 决定 |
| 把用户历史日记塞进 Prompt 做「个性化解读」 | **收**（不做） | 简报 §26 与 G-13 双重禁止。日记只供用户自己回顾 |
| 用 LLM 生成牌面插画 / 配图 | **收**（不做） | 与本轮价值无关，且违反 §21 的统一牌背与统一设计语言 |
| 缓存解读结果到服务端 / 建解读库 | **收**（不做） | 需要服务端持久化，越过 G-17 未解除部分。解读结果继续只存 localStorage |
| Prompt 里塞进 78 张牌的完整牌义数据 | **收**（不做） | 只发**本次抽到的牌**的元数据。全量牌库会撑爆上下文、抬高成本，且给了 LLM「换一张更合适的牌」的素材 |
| 「换个角度再解读一次」按钮（同一副牌重新生成不同解读） | **放**（P2，条件通过） | 不动牌、不重抽，只重新调用同一 payload，属于用户对**解读**而非对**牌**的重试。但必须与 Retry 共用同一条 payload 构建路径，且新解读覆盖旧解读、不产生多份并存 |
| Token 用量 / 成本展示给用户 | **收**（不做） | 用户不需要知道，展示它会把注意力从牌面拉到技术细节上 |

## 3. 功能清单与优先级

> **P0**：不做则本轮不成立。**P1**：完整体验所需。**P2**：加分项，时间不足可砍。
> 「为什么服务于『让解读真正像读牌』」一列若无法回答，该功能自动降级或砍掉。

| # | 功能 | 优先级 | 为什么服务于「让解读真正像读牌」 |
|---|---|---|---|
| V01 | `ReadingProvider` 接口 + Mock / DeepSeek 双实现 + `READING_PROVIDER` 切换 | P0 | 让「真解读」可以被随时替换回「可用的解读」，保证任何时候都读得到牌 |
| V02 | 服务端解读端点（Key 仅在服务端） | P0 | 前置条件：不安全就不能上线，上线不了就没有真解读 |
| V03 | 请求 payload 构建器（唯一入口，纯函数，输入=已冻结的 Session 快照） | P0 | 牌在发出去之前就已定死，是「LLM 不参与抽牌」的结构性保证 |
| V04 | 结构化 JSON 契约（§4）+ 服务端 Schema 校验 | P0 | 结构化才能让「关系分析」「叙事」「回答问题」各自有位置，而不是糊成一坨长文 |
| V05 | 卡牌身份回显校验（响应中的牌必须与请求逐张一致） | P0 | 唯一能机器验证「LLM 没换牌/没加牌/没改正逆位」的手段 |
| V06 | Card Relationship 分析（11 类信号，有意义才输出） | P0 | **本轮最核心的价值**：牌与牌之间产生关系，解读才不再是字典 |
| V07 | 整体叙事 narrative（开始→中间→结尾） | P0 | 把牌串成一个故事，而不是 N 段独立点评 |
| V08 | `answerToQuestion` 回到用户最初的问题 | P0 | 用户抱怨的「没结合最初问题」的直接解药 |
| V09 | 10 类错误全覆盖 + 统一失败文案 + 牌不丢失 | P0 | 失败时牌还在，用户才敢再试；白屏一次就再也不会用真解读 |
| V10 | Retry：payload 逐字节相同，绝不重抽 | P0 | 重试是重读，不是重抽。重抽一次就摧毁了 V1 建立的全部信任 |
| V11 | 语言红线运行时校验（禁语 + 空洞表达） | P0 | LLM 的输出不可穷举，V1 的静态检索方式在 V2 失效，必须运行时挡 |
| V12 | V1 `Reading` 兼容层（历史日记不被破坏） | P0 | 用户的日记是产品资产，破坏一次就是数据事故 |
| V13 | 已生成的解读不重复调用（刷新/回退不重发请求） | P0 | 刷新页面解读变了 = 用户会怀疑「牌是不是也变了」 |
| V14 | 本地 `safety.ts` 判定结果注入 Prompt 作为硬约束 | P1 | 安全边界保持确定性，不外包给模型 |
| V15 | Loading 分阶段文案（描述系统动作，非思维链） | P1 | 解读需要十几秒，没有阶段感用户会以为卡死；但假思维链是欺骗 |
| V16 | 隐私一次性告知 + 可选择继续用 Mock | P1 | V1 全程本地，V2 第一次把用户的问题发出设备，必须让用户知道 |
| V17 | 并发去重与节流（同一 Session 同时只允许一个在途请求） | P1 | 防止连点重复烧 token，也防止两份解读竞态写入 |
| V18 | 模型可配置（`deepseek-v4-pro` 默认 / `deepseek-v4-flash`），`max_tokens` 给足防截断 | P1 | 截断的 JSON = 必然失败；模型可切换是成本与质量的调节旋钮 |
| V19 | 空 content 自动重试一次（官方文档已提示会偶发） | P1 | 已知的、可自动恢复的失败，不该让用户看到错误 |
| V20 | Reading 结构里记录 `provider` / `model` / `generatedAt` | P2 | 让 QA 与日记能区分「这条是真解读还是 Mock」 |
| V21 | 「换个角度再解读一次」（不动牌，覆盖旧解读） | P2 | 同一副牌的第二种读法是真实读牌习惯，但优先级低于把第一次读好 |
| V22 | 服务端基础限流（按 IP / 简单令牌桶） | P2 | 防滥用；本轮无账号体系，只做最粗一层 |

## 4. 结构化输出契约（产品层，字段语义）

> 字段名与嵌套形状由 Architect 定稿，本节只定义**产品语义与硬约束**。QA 按本节验收。

| 字段 | 类型 | 产品语义 | 硬约束 |
|---|---|---|---|
| `readingTheme` | string | 这次牌阵的主导主题，一个短句 | 非空；不得是牌名的简单罗列 |
| `overallEnergy` | string | 整组牌的整体基调 | 非空；不得使用「能量告诉你」式表达 |
| `cards[]` | array | 每张牌在**它所在牌位上**的解释 | 长度、顺序、`positionId`/`cardId`/`orientation` 必须与请求**逐张全等** |
| `relationships[]` | array | 牌与牌之间的关系，每条含类型、涉及的牌位、洞察 | **0 条合法**；每条必须指名 ≥2 个牌位；单张牌阵允许为空 |
| `narrative` | string | 把牌按开始→中间→结尾串起来的整体叙事 | 非空；必须出现 ≥2 个牌位/牌名的指代（单张牌阵除外） |
| `answerToQuestion` | string | 在用户最初问题的语境下的回应 | 非空；必须可追溯到用户问题；不得给出确定性预测 |
| `reflectionQuestions[]` | string[] | 留给用户自己想的问题 | 2–4 条；必须是问句；不得是伪装成问句的断言 |
| `safetyNotice` | string \| null | 高风险提示 | **由服务端本地 `safety.ts` 决定并覆盖**，不采信模型的判断 |

**关系分析的 11 类信号**（S4）：大小阿卡纳密度、花色重复、元素重复、元素冲突、数字模式、正逆位比例、相邻牌位、开始→中间→结尾、支持牌、冲突牌、转折点 / 主导主题。
**硬约束**：只在牌面**真的呈现**该信号时才输出对应条目。禁止为了凑满 11 类而输出「本次没有明显的元素冲突」这类空条目——**没有就不写**。

## 5. V2 新增验收标准 AC-V2-xx

> Given / When / Then，QA 可客观验证。V1 的 AC-01~15 全部继续有效。

### AC-V2-01 LLM 绝对不参与抽牌
- **Given** 用户处于 `/reading`，牌阵所有牌位均已摆满且全部 `revealed = true`
- **When** QA 检查解读请求的发起时机与调用链
- **Then** 请求发出的时间戳必须晚于最后一张牌的 `revealedAt`；请求构建函数的输入只有已冻结的 Session 快照，其调用链中不得出现任何随机数生成、`buildHiddenDeck`、`shuffle`、`cut`、`cardAt` 的写操作
- **And** 全流程中不存在「牌翻开前预取解读」「边翻边请求」的行为

### AC-V2-02 API Key 不出现在任何前端产物
- **Given** 执行 `npm run build`
- **When** QA 对 `dist/` 全量检索 Key 明文、`sk-` 前缀、`api.deepseek.com`、`Authorization`
- **Then** 全部零命中
- **And** 源码中不存在任何 `VITE_` 前缀的 Key 相关变量；不存在硬编码 Key；仓库中不存在被提交的 `.env`，只存在 `.env.example`
- **And** 浏览器 Network 面板中不存在任何指向 `api.deepseek.com` 的请求，只有指向本站服务端端点的请求

### AC-V2-03 结构化输出被正确渲染
- **Given** 一次成功的在线解读
- **When** QA 检查 Reading 页渲染结果
- **Then** `readingTheme / overallEnergy / cards / relationships / narrative / answerToQuestion / reflectionQuestions` 各自渲染在独立区块，且遵循 V1 AC-10 的「先短后长」（核心结论常驻，其余默认折叠）
- **And** 页面上不出现任何原始 JSON、花括号、`**`、`##` 等 Markdown 标记
- **And** 前端代码中不存在对模型返回文本的 Markdown 解析或正则切段

### AC-V2-04 关系分析真实且不硬凑
- **Given** 一个三张及以上的牌阵，其中不存在元素冲突
- **When** 解读生成成功
- **Then** `relationships[]` 中不出现「没有明显元素冲突」这类空内容条目
- **And Given** 一个牌阵中出现了 ≥2 张同花色的牌
- **Then** `relationships[]` 中必须出现一条指向该花色重复的条目，且指名了具体的牌位
- **And** 每条关系至少涉及 2 个牌位（单张牌阵可为 0 条）

### AC-V2-05 失败不丢牌、不白屏
- **Given** 服务端分别模拟：Key 缺失 / 401 / 403 / 429 / 5xx / 网络错误 / 超时 / 非法 JSON / 空 content / Schema 校验失败，共 10 种
- **When** 用户在 `/reading` 触发解读
- **Then** 每一种都必须渲染出可读的错误态，页面不白屏、不崩溃、控制台无未捕获异常
- **And** 文案为：「这次解读没有成功完成，你抽出的牌仍然保留，可以重新尝试解读。」
- **And** 牌阵缩略条与所有已翻开的牌仍然正常显示；`session.placements`、`session.deck` 未被修改
- **And** 页面上提供「重新尝试解读」入口

### AC-V2-06 Retry 不重抽且 payload 完全相同
- **Given** 一次解读已失败
- **When** 用户点击「重新尝试解读」
- **Then** 第二次请求的 payload 与第一次**逐字节相同**（question / spreadId / positionId 顺序 / cardId / orientation / 牌义元数据全等）
- **And** `session.deck`、`session.placements`、`revealed` 状态在重试前后完全不变
- **And** 连续重试 3 次，三次 payload 两两相同

### AC-V2-07 Mock 模式随时可用
- **Given** 服务端未配置 API Key，或 `READING_PROVIDER` 被设为 mock
- **When** 用户走完完整流程进入 `/reading`
- **Then** 解读正常生成（内容来自 `mockReading.ts`），全流程无报错、无「配置错误」阻断
- **And** 简报 §28 的完整交付流程在无 Key 环境下 100% 可跑通

### AC-V2-08 语言红线
- **Given** 任意一次在线解读的最终渲染文本
- **When** QA 全文检索
- **Then** 不得出现确定性/宿命论表述（`FORBIDDEN_PHRASES` 语义集）
- **And** 不得出现空洞玄学表达：`宇宙`、`命运`、`能量告诉你`、`牌绝对说明`、`天机`、`注定`
- **And** 「不一定 / 说不定 / 不必」等**含禁语子串但语义相反**的表达不得被误判为违规
- **And** 文本中应出现「这组牌更倾向于 / 如果把这几张牌联系起来看 / 在你当前的问题背景下」这一类相对化句式
- **And** 命中红线时：服务端重试一次；仍命中则降级为 Mock 解读并在结构上标记 `provider = mock`，而不是把违规文本送到前端

### AC-V2-09 历史日记不被破坏
- **Given** localStorage 中存在若干条 V1 结构的日记记录（`reading.headline` / `cardAnalyses` / `relations` / `trend` / `watchOut` / `actions`）
- **When** 部署 V2 后打开 `/journal`、`/journal/:id`、`/share/:id`
- **Then** 列表摘要（`toSummary` 的 `headline`）、详情页、分享页全部正常显示，无 `undefined`、无空白、无崩溃
- **And** V2 新生成的记录同样能在这三个页面正常显示
- **And** 新旧两种记录可以在同一个列表中共存并正确排序

### AC-V2-10 卡牌身份回显一致性
- **Given** 模型返回的 `cards[]` 中有任意一张的 `cardId` / `orientation` / `positionId` 与请求不一致，或数量不等，或出现请求中不存在的牌
- **When** 服务端校验该响应
- **Then** 该响应必须被判定为失败（等同 Schema 校验失败），不得渲染到前端
- **And** 走 AC-V2-05 的失败路径（牌保留 + 可重试）

### AC-V2-11 解读不重复生成
- **Given** 一次解读已成功并写入 `session.reading`
- **When** 用户刷新 `/reading`、或从 `/table/reveal` 返回、或从日记再次进入
- **Then** 不再发起任何新的解读请求，展示的是已保存的那一份
- **And** 牌阵、牌面、正逆位与刷新前完全一致（V1 AC-08 / G-22 的延伸）

### AC-V2-12 Loading 分阶段但不伪装思维链
- **Given** 一次在线解读正在进行
- **When** QA 观察加载态文案
- **Then** 文案只描述系统正在做什么（如「正在整理牌阵结构」「正在联系解读服务」「正在校验解读结果」）
- **And** 不得出现第一人称的模型内心独白、不得出现「我注意到…」「让我想想…」这类伪装成推理过程的文案
- **And** 不得出现与真实进度无关的虚假进度条百分比

### AC-V2-13 超时与截断处理
- **Given** 服务端设置了明确的请求超时上限
- **When** DeepSeek 响应超时、或返回被 `max_tokens` 截断的非法 JSON、或返回空 content
- **Then** 空 content 自动重试一次（用户无感）；仍失败则走 AC-V2-05 失败路径
- **And** `max_tokens` 配置必须足以容纳完整结构化输出，QA 在 5 张牌阵上验证输出未被截断

### AC-V2-14 安全边界仍由本地判定
- **Given** 用户问题命中 `safety.ts` 的医疗/财务/法律/危险行为关键词
- **When** 解读生成
- **Then** `safetyNotice` 由本地 `detectRisk` 决定并写入最终结果，不采信模型返回的对应字段
- **And** 该情形下的解读文本不得包含确定性预测（V1 AC-11 / G-14 继续有效）

### AC-V2-15 追问仍为 Mock 且 Context 不外溢
- **Given** 用户在 Reading 页追问
- **When** QA 检查调用链与网络请求
- **Then** 追问不产生任何对 DeepSeek 的请求，仍走 `answerFollowUp`
- **And** V1 AC-12 继续成立

### AC-V2-16 请求体最小化
- **Given** 一次解读请求
- **When** QA 检查发往服务端与发往 DeepSeek 的 payload
- **Then** 只包含：用户最终采用的问题、牌阵与牌位定义、本次抽到的牌及其正逆位与牌义元数据、安全判定结果
- **And** 不得包含：完整 78 张 `deck` 数组、未翻开的牌、`shuffleSeed`、`interactionEntropy`、历史日记、用户的 mood/note/outcome

## 6. V2 新增红线 GV2-xx（出现即打回）

**GV2-01** LLM 的任何输出被用于决定或修改 `deck`、`placements`、`orientation`、`spreadId`——包括「建议再抽一张」「这张牌其实更适合放在…」。
**GV2-02** 在最后一张牌翻开之前发起解读请求（含预取、预热、并行调用）。
**GV2-03** 解读文本中出现「我为你抽到了」「我帮你换了一张」「让我们重新洗牌」这类暗示模型参与抽牌的表达。
**GV2-04** API Key 出现在前端代码、构建产物、`VITE_*` 变量、localStorage 或任何客户端可见位置；或浏览器直连 `api.deepseek.com`。
**GV2-05** `.env` 被提交进仓库；或 Key 被硬编码在任何源文件中。
**GV2-06** 前端对模型返回的长文本做 Markdown 解析、正则切段或字符串拆分来还原结构。
**GV2-07** 解读失败导致白屏、崩溃、路由跳走、或 `session.deck` / `session.placements` 被清空、重置、重新生成。
**GV2-08** Retry 时重新抽牌、重新洗牌、或 payload 与首次不一致。
**GV2-09** 移除或架空 `MockReadingProvider`，导致无 Key 环境下产品不可用。
**GV2-10** `relationships[]` 出现为凑字段而写的空条目（「本次没有明显的 X」），或 `cards[]` 中出现与请求不符的牌。
**GV2-11** 加载态伪装成模型思维链 / 伪造进度百分比。
**GV2-12** 语言红线校验被跳过、被降级为警告、或违规文本被直接渲染给用户。
**GV2-13** V2 上线后 V1 结构的历史日记在列表/详情/分享任一页出现 `undefined`、空白或崩溃。
**GV2-14** 把用户历史日记、多次 Session、或未翻开的牌塞进 Prompt。
**GV2-15** 安全边界（高风险提示）改由模型判定。
**GV2-16** 借本轮之机重构 UI、随机引擎、78 张牌数据、导航结构，或删除任何现有页面。

## 7. 与 V1 Guardrails 的关系

**默认结论：V1 的 G-01 ~ G-24 在本轮全部继续有效，一条都不解除**，唯一例外见下方 G-17 的修订。

重点重申（本轮最容易被 LLM 接入撞破的六条）：

| V1 红线 | 在 V2 的具体含义 |
|---|---|
| **G-01** 点击后才 random | 依然成立。V2 额外要求：LLM 调用链中不得出现任何影响牌面的调用。请求只读已冻结快照 |
| **G-02** Hidden Deck 中途重生成 | 依然成立。解读失败、重试、降级 Mock —— **三种路径都不得触发 `startSession` / `buildHiddenDeck`** |
| **G-11** AI 抢先发言 | 依然成立。`/table/reveal` 仍需用户手动点「开始完整解读」；解读请求只能在 `/reading` 挂载后发起，禁止在翻牌页预取以「优化等待体验」 |
| **G-12** AI 参与决定抽哪张牌 | 本轮最高优先级。牌阵推荐、问题优化保持 Mock；LLM 只接收结果，其输出经 AC-V2-10 逐张回显校验 |
| **G-13** Follow-up 变通用 Chatbot / 读历史日记 | 依然成立且加强：追问本轮不接 LLM；Prompt 中永远没有历史日记的入口（`buildReadingInput` 仍是唯一组装点） |
| **G-14** 宿命论 / 确定性预测 | 依然成立，但**校验方式必须升级**：V1 靠对静态文案全文检索即可穷举，V2 的文本来自模型、不可穷举，必须改为服务端运行时校验 + 违规降级（AC-V2-08）。沿用 V1 `FORBIDDEN_PHRASES` 时须处理「不一定 / 说不定」这类子串误判 |

**G-17 的本轮修订（唯一一处放宽，需 QA 明确知晓）**：
V1 的 G-17 原文为「使用真实 AI API、云数据库、真实登录、付费入口」。本轮用户明确要求接入 DeepSeek，因此 **G-17 中「真实 AI API」一项在 V2 解除**。
**其余三项（云数据库、真实登录、付费入口）继续有效**——服务端只做解读转发，**不得**引入数据库、账号体系、计费。所有用户数据（Session、日记）继续只存 localStorage。

## 9. Gate 1 (Product) 自检结论

- Scope 已闭合：新增一个 Provider 抽象、一个服务端端点、一套结构化契约，不新增页面、不改导航、不动随机引擎与牌库。
- 核心价值可被三条客观标准检验：牌与牌有关系（AC-V2-04）、有整体叙事（§4 `narrative`）、回到最初的问题（§4 `answerToQuestion`）。
- 「LLM 不参与抽牌」不依赖承诺，而是由三道机器可验的关卡保证：调用时机（AC-V2-01）、payload 只读冻结快照（V03）、响应逐张回显校验（AC-V2-10）。
- 最坏情况下（无 Key / API 全挂）产品仍完整可用（AC-V2-07），V1 的交付标准不受影响。
- 历史数据兼容有独立验收项（AC-V2-09）与独立红线（GV2-13），不靠「应该没事」。

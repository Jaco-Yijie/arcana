## 1. Executive Summary

Arcana 现在是一个**内核完成度很高、外壳还停留在上一阶段**的产品。

抽牌仪式、解读质量、错误恢复、离线兜底、reduced-motion —— 这几块已经是完成品水准，
有些甚至超出预期（解读会明确拒绝替用户做决定；390 张原画全挂掉时流程依然完整可用）。

问题几乎全部集中在一条线上：**产品的信息架构还停留在「原画没画完」的那个时期。**
390 张真实原画在 Phase C3 落地了，但：

- Deck Library 仍把 5 套 **0/78 的空壳**放在主位，首屏就是 `DEV FIXTURE / NOT REAL ARTWORK`；
  78/78 的那 5 套被降级到下面，标题写着「现行牌组」，文案说「上面五套的插画还在制作中」——**这句话已经反了**
- UI 的卡牌尺寸仍是按程序化 SVG 的信息密度定的：Reveal 107px、Reading 62px、Journal 62px。
  实测**程序化兜底图在同一尺寸下比真实原画更易读** —— 这就是「Artwork 不是第一视觉层」最直接的证据
- Desktop 仍是手机布局居中：1920 上牌宽 146px，1024 上牌宽 94px（**比 360px 手机上的 100px 还小**）

另有一条真正的功能失效：**「继续追问」完全没有输出**。状态写入正常，但渲染分支在 v2.3 重构时被落下了。

**本轮新增 P0：1 条**（有完整复现与代码定位）。

## 2. Full User Journey

两条入口都完整走通，真实 DeepSeek，未跳步。

### 带着问题来（5 张牌 · 深度解读）

```
/ → /decks → /question?mode=question → （问题优化）→ /spread → /focus
  → /table/shuffle → /table/cut → /table/draw → /table/reveal → /reading → /journal
```

实测节点：洗牌 8 次手势后出现「洗好了」· 切牌拖到「大约第 74 张」· 抽牌 5/5 拖拽落位
· 翻牌 5/5 · 深度解读 **131s / 约 900 字** · 标准解读 **57s / 576 字** · 存入日记成功。

一处与预期不同：**「带着问题来」先进 `/decks` 选牌组，再进问题页。**
牌组选择被放在了用户还不知道自己要问什么之前。

### 随缘抽一张

```
/ → /question?mode=random → （直接随缘）→ /focus → …（同上仪式）
```

跳过 `/decks` 与 `/spread`，自动用单张牌。**两个入口没有塌缩成同一流程**（§4 通过）。
但随缘一张牌仍要完整走完洗 → 切 → 摊 → 选 → 摆 → 翻，这一点见 §10 的开放问题。

### Resume Session

中断在 `/table/shuffle` 后回首页，顶部出现
「你有一次未完成的抽牌 / 随缘抽一张 · 单张牌 · 已摆 0/1」+ `继续（洗牌）` `重新开始`。
**阶段名准确，恢复可用。**

## 4. KEEP Pages（8）

**QuestionPage** — 一屏、不滚动、文案克制（「现在，把你最想弄清楚的一件事放在这里。」），
三条出路（继续 / 没想好怎么问 / 我暂时没有具体问题）层级正确。

**Spread 推荐** — 按问题类型给 3 个推荐 + 「查看全部牌阵」兜底，并明说「推荐只是建议，选哪个由你决定」。

**Focus / Ritual** — 「直接开始」与「专注一下」并置，不强迫仪式。

**Shuffle** — 本轮体验最好的一页。滑动才洗、洗了才出 CTA、实时显示「已洗 8 次」。
**操作感、随机感、仪式感三条都成立**，不是「点几个按钮」。

**Reading 深度选择** — 标准 / 深度两张卡片写清了各自包含什么、大概多久。实测两档产出确实不同
（深度的 summary 会谈牌与牌的呼应，标准不会），不是文案糊弄。

**Journal 空态** — 「还没有记录。」+「去抽一张」，干净。

**Settings** — 3 个开关 + 摊牌模式，一屏放下，底部一句「所有记录只保存在这台设备的浏览器里，不会上传」。

**Error / Retry** — 见 §18，本轮质量最高的一块。

## 8. 重点审查：首页

**结论：POLISH，不是 REDESIGN。**

首页的**内容是对的**，问题在于它只为手机设计过。

做对了的：
- 副标题「亲手洗牌、切牌、摊牌、翻牌 —— 牌由你自己抽出。」**一句话说清了 Arcana 的核心特点**，§8 的最后一问答案是「理解得了」
- 两个入口的主副标题层级清楚，用户知道选哪个
- Resume 提示插在最顶部，阶段名准确
- 移动端（390×844）比例舒服，留白得当，仪式感成立

需要 POLISH 的：

| 问题 | 证据 | 严重度 |
|---|---|---|
| **≥768 后所有视口逐像素相同**，内容列锁死 600px，1920 上只是空白更多 | 7 档视口 `scrollH` 全等于视口高，H1 与两个按钮在 768/1024/1440/1920 上尺寸位置完全一致 | P3 |
| 首页零 Artwork —— 产品最大的视觉资产在门口完全缺席 | `home-d1440.png` | P2 |
| 两个入口卡片读起来像表单行（等高圆角矩形 + 主副文案），不像两扇门 | 同上 | P3 |
| 底部导航偏弱：`牌组` `设置` 触达宽度仅 27px | probe 全视口报 `touch target <44px` | P2 |

「首页是否太像普通表单」——**是，但只在桌面端。** 手机上它是一个克制的仪式入口；
桌面上同一套布局居中之后，就变成了一张 600px 宽的表单卡片浮在 1920 的黑底上。

## 9. 重点审查：Deck Library

**结论：REDESIGN。这是本轮对「完成品感」伤害最大的一页。**

### 实测数字（`decks-m390-full.png` / `decks-d1440-viewport.png`）

| 指标 | 值 |
|---|---:|
| 牌组行数 | 10 |
| 「素材未提供」出现 | **22 次** |
| 「封面未提供」出现 | **9 次** |
| 「素材备齐后开放」 | 5 次 |
| 显示 0 / 78 的牌组 | 4 |
| 显示 78 / 78 的牌组 | 5 |
| 页面高度 | 移动端 4474px（**5.3 屏**）· 桌面 4351px |

### 三个结构性问题

**① 主位给了空壳，成品被降级。**
`DeckLibraryPage.tsx:269` 先渲染 `artworkDecks`（空灵/极乐之影/蛋白潮汐/仙境之影/经典，合计 3/390 张），
再在 `mt-2` 的分隔线下渲染 `legacyDecks`（月光/古典/森语/星图/幽影，**390/390 真实原画**），
分组标题写「现行牌组」，说明文案写：

> 上面五套的插画还在制作中，这几套现在就能用。

Phase C3 之后这句话已经与事实相反。**首屏第一眼就是 `DEV FIXTURE` / `NOT REAL ARTWORK`。**

**② 5 套成品牌组的封面位全是空的。**
封面是这一页自己定义的「第一视觉入口」（源码注释原话），但 `hybridManifest` 的
`deck: { cover: null, back: null }` 让 5 套 78/78 的牌组全部显示「封面未提供」虚线框。
一个 164px 宽的空框旁边挂着 5 张漂亮的真实原画 —— 视觉重心完全错位。

**③ 页面 5.3 屏，扫视不成立。**
源码注释明确写着「画廊要能扫视才成立」，但 10 行 × 每行约 420px 之后，
用户要滚 4 屏才能看到第一套能用的牌。

### 逐条回答 §9 的检查项

| 检查 | 结论 |
|---|---|
| 一眼知道五套真的不同 | **能** —— 5 张同牌的扇形对比是这一页做得最好的地方，画风差异一目了然 |
| 显示真实 Artwork | 成品牌组**是**；主位那 5 套**不是** |
| 展示 3–5 张代表牌 | 是，5 张，且八套用同一批牌（同一个模特拍多组照片），方法论正确 |
| 有风格说明 | 有（tagline + 展开态 description） |
| 当前选中 Deck 明确 | 明确（边框变亮 + 「使用中」+ `aria-checked`） |
| 切换有明显视觉反馈 | 有，但克制（`scale 0.995 → 1`），在长页面里容易被忽略 |
| 是否有 0/78 / Coming Soon 残留 | **有，而且是主位** |
| 是否仍像普通设置列表 | **不像** —— 这一点做对了，它确实是牌柜不是列表 |
| 是否值得增加「查看牌组」入口 | 已有（「看看这套」展开），但入口文案弱、位置在行底右侧，不易发现 |

### 建议方向（不在本轮实施）

1. 把 `legacyDecks`（成品）提到主位，`artworkDecks`（未开工）本轮**不陈列**
2. 封面位回退到该牌组自己的一张代表牌或卡背，消灭「封面未提供」
3. 「现行牌组」这个分组名与那句说明文案一并删除

## 10. Artwork Priority Audit

> 原则：**Artwork = 第一视觉层，UI = 第二视觉层。**

### 实测卡牌宽度（CSS px，全视口）

| 页面 | 360 | 390 | 430 | 768 | 1024 | 1440 | 1920 |
|---|---:|---:|---:|---:|---:|---:|---:|
| Reveal | 100 | 107 | 122 | 137 | **94** | 116 | 146 |
| Reveal（牌义面板开着）| 55 | 64 | 81 | 97 | 94 | 116 | 146 |
| Reading 顶部牌条 | 62 | 62 | 62 | 62 | 62 | 62 | 62 |
| Journal 缩略图 | 62 | 62 | 62 | 62 | 62 | 62 | 62 |

三条结论：

**① Desktop 1024 上的牌（94px）比 360px 手机上的（100px）还小。**
这不是「桌面没优化」，是布局在 1024×768 这个矮宽比下退化了。

**② Reading 与 Journal 的牌宽全视口恒定 62px。** 1920 的屏幕和 360 的手机拿到同样大小的牌。

**③ 决定性证据：程序化兜底图在同尺寸下比真实原画更易读。**
`NOART=1` 注入（所有 `/assets/decks/**` 返回失败）后，兜底 SVG 在 107px 下
牌名大、符号清晰、正逆位明确（`errors/artwork-missing-fallback-m390.png`）；
而真实原画在同一尺寸下细节全糊、烘焙的罗马数字被压扁到不可读
（`reading/card-label-overlap-zoom.png`）。
**UI 的尺寸体系是按程序化 SVG 的信息密度定的，还没有跟着 Artwork 升级。**

### 逐条回答

| 检查 | 结论 |
|---|---|
| 卡是不是太小 | **是**，全流程都偏小 |
| UI 文本是否比牌更抢 | Reveal 与 Reading 是的（牌义面板 / 正文占据主视觉） |
| 背景是否影响牌面 | 否。星空背景很克制，没有干扰 |
| 卡周围留白是否不足 | 移动端够；桌面端**过多**（1920 上牌阵两侧+中央大片死区） |
| Reveal 是否有「翻开真实牌」的冲击 | **不够**，见 §11 |
| Reading 中牌是否缩得太小 | **是**，62px |
| Journal 中牌是否退化成无意义 thumbnail | **接近**。62px 下能认出是哪张，但看不出画 |

### 开放问题（非缺陷）

随缘抽一张只抽 1 张，却要完整走 78 张的洗 → 切 → 摊 → 选 → 摆 → 翻。
仪式感与轻量入口在这里有张力，本轮不判定，列入 §25。

## 11. Reveal Audit

「用户第一眼应该先看到 Card，然后才看到 Meaning」—— 当前是**同时**看到，
而且 Card 因为要给 Meaning 让位而变小了。

## 12. CardMeaningSheet Audit

**结论：POLISH。组件质量高，尺寸策略有问题。**

Mobile：Bottom Sheet 高度约占 30%，可拖动手柄、backdrop、Escape、点击外部、明确关闭按钮 —— **四条齐全**
（源码注释记录了旧版只有一根小灰条的问题，已修复）。内部可滚动。
唯一问题是它把牌从 107px 压到 64px。

Desktop：右侧面板，**牌与面板可同时可见**（§14 要求满足）。但：
- 面板约 470px 宽、整屏高，实际内容只有 4 行（牌名 / 正逆位 / 关键词 / 查看详细牌义）→ **95% 空白**
- 面板压住了「开始完整解读」按钮的右端（`sheet-d1440.png`）

**「百科说明」还是「帮助理解刚抽到的牌」？**
当前是**前者偏多**：显示的是这张牌的通用关键词（「倦怠 · 视而不见 · 内向沉思」），
没有任何一句与「你现在的问题」或「它落在哪个牌位」相关。
牌位名（现状 / A 结果）就在牌下方，但面板里完全没有用上。

## 14. Follow-up Audit — 本轮唯一 P0

### 现象

在 `/reading` 底部输入框输入内容并点「发送」后，**页面没有任何变化**：
问题不显示、没有回答、没有加载态、没有报错。

### 复现

1. `npm run dev`，走完任意一次抽牌到 `/reading`，完成解读
2. 在底部「关于这次抽牌继续问…」输入任意文字
3. 点「发送」（或按 Enter）
4. 等待 120s

### 实测

```
[追问] 输入框值 = "如果我先不做决定，只是再观察一个月呢？"
[追问] 发送按钮 disabled = false
[追问] 点击前 followUps = 0
[追问] 点击后 followUps = 2      ← 状态写入成功
[追问] 输入框现在 = ""            ← 已清空
[追问] 按 Enter 后 followUps = 4  ← 再次成功
   [3s]   正文 581 字（发送前 581）· 含追问文本=false
   [120s] 正文 581 字（发送前 581）· 含追问文本=false
```

无网络请求（**符合设计**：`followUp.ts` 明确不接 LLM，AC-12 / G-13），无 console 输出。

### 根因

追问消息列表写在 `src/pages/ReadingPage.tsx:294`：

```tsx
{session.followUps.length > 0 && (
  <div className="mt-6 flex flex-col gap-3">
    {session.followUps.map((m) => ( … ))}
```

这段位于 **legacy `reading` 渲染分支**内（同分支的 Accordion 标题是
「综合趋势」「值得注意的问题」「可以考虑的行动方向」）。

而 v2.3 之后实际渲染的是 `src/features/reading/ReadingSections.tsx` 的**结构化路径**
（Accordion 标题是「每张牌的分析」「牌与牌之间的关系」「整体走向」「可以再想想的问题」——
与真实页面一致）。`ReadingPage.tsx:59` 的 `hasReading` 同时接受两种，
但只要 `structuredReading` 存在就走新路径，**legacy 分支永不挂载**。

输入框渲染在两个分支之外，所以它始终可见、可用、可写状态 —— 功能看起来是活的，
但输出被留在了一个不会渲染的分支里。

### 为什么算 P0

§3 把「继续追问」列为必走流程，§17 为它单列一节。它当前 **0% 可用且零反馈**——
用户会以为自己输入有问题，反复重试。虽然不阻断「保存日记 / 回首页」，
但对这个功能本身是完全阻断。

## 20. Card Label Audit

**当前状态：不是三重重复，是「原画标题被破坏 + UI 标题覆盖」。**

放大取证（`reading/card-label-overlap-zoom.png`，月光 / 月亮 / 现状位，107px 实际渲染）：

- **顶部**：原画烘焙的罗马数字 `XVIII` 与装饰边框被压扁到**完全不可读**，成为一条模糊色带
- **底部**：原画自己的英文题字带（`The Moon` + 花边）**被 UI 的深色渐变遮罩盖住**
- **渐变之上**：UI 绘制中文「月亮」（逆位时下方再加金色「逆位」）
- **牌外**：牌位名「现状」

也就是说，C4 QA 记录的 P2「原画英文题字与 UI 中文标签重叠约 4px」，
在真实产品里的表现比记录**更严重**：不是重叠，是**原画题字整条被盖掉**。

### 逐页现状

| 页面 | 原画 title | UI 中文名 | UI 英文名 | 正逆位 | 位置名 |
|---|---|---|---|---|---|
| Reveal | 被渐变盖住 | ✅ 牌上 | — | ✅ 牌上 | ✅ 牌下 |
| CardMeaningSheet | （同上，牌仍在） | ✅ 面板 | ✅ 面板 | ✅ 面板 | ❌ 面板未用 |
| Reading 牌条 | 62px，不可读 | ❌ | ❌ | ❌ | ✅ 牌下 |
| Journal | 62px，不可读 | ❌ | ❌ | ❌ | ❌ |

同屏最多出现次数：**Reveal + 面板打开时，牌名出现 3 次**（牌上中文 / 面板中文 / 面板英文）。

### 建议（只给方向，本轮不动）

| 页面 | 建议保留 |
|---|---|
| Reveal | 牌大到能读原画题字 → **撤掉牌面上的 UI 中文名与渐变遮罩**；正逆位与位置名留在牌外 |
